================================================================================
DUR API - Endpoint Reference
================================================================================

This is a plain-text quick reference for every API endpoint: what it needs to
be called (auth, parameters, request body) and what it returns. This mirrors
the interactive Swagger docs at /api/documentation, which also show live
request/response examples and let you try each endpoint directly.

--------------------------------------------------------------------------------
GENERAL
--------------------------------------------------------------------------------

Base URL:        /api
Authentication:   Bearer token in the Authorization header, e.g.:
                   Authorization: Bearer <clerk_session_token>
                  The token comes from Clerk (frontend auth). There is no
                  separate login endpoint on this API.

Content-Type:     application/json for all endpoints EXCEPT the ones that
                  accept file uploads (creating/updating products or
                  categories), which must be sent as multipart/form-data.

Error format (all errors, any endpoint):
    {
      "message": "Human-readable message",
      "errors": { "field_name": ["Reason"] }   // present only on 422 validation errors
    }

Common status codes across all endpoints:
    401  Not authenticated (missing/invalid Clerk token)
    403  Authenticated but role not allowed (see "Auth" per endpoint below)
    404  Resource not found
    422  Validation failed (see "errors" object)

How an order happens right now: there is no cart or checkout in this API.
The customer sends a product link to management over WhatsApp, and
management sets a discount on that product through
PUT /api/products/{product}. The promotions section further down is built
for a later version and is not part of that flow.

Roles: admin, manager, customer (default for every new user).
Role is stored in OUR database (users.role), NOT in Clerk. Clerk only proves
identity; it has no concept of role. New users always start as "customer".
There is no API endpoint to change a role - it must be done on the backend:
    php artisan user:set-role user@example.com admin

================================================================================
SETTINGS
================================================================================

The editable content of the site - brand, contact details, social links and
the home page hero. ONE object, never a list: there is a single settings
record and every key is always present, so no existence checks are needed.

It ships pre-filled, so GET works from day one without anyone saving
anything first.

--------------------------------------------------------------------------------

GET /api/settings
    Auth:     none - public, no login required
    Params:   none
    Returns:  the Settings object (see the shape below)

--------------------------------------------------------------------------------

PUT /api/settings
    Auth:     admin only (manager is NOT enough)
    Body:     application/json, or multipart/form-data when uploading media
    Update:   PARTIAL. Send only the sections and fields that change;
              anything omitted keeps its stored value. Send an explicit null
              to clear a field.

    Field rules:
        brand.whatsapp_number   digits only, no "+" and no spaces.
                                Required whenever the brand section is sent,
                                so it can never end up empty - but updating
                                another section does not need to resend it.
        brand.site_url          full URL or null
        contact.email           valid email or null
        contact.phone           free text - the version shown to visitors
        contact.phone_href      free text - goes straight into href="..."
                                Kept separate on purpose: the display format
                                is not a valid tel: value.
        social.*_url            full URLs only (https://...)
        home_hero.*_button_url  a relative path ("/products", "/#about") OR a
                                full URL - NOT validated as a URL
        everything else         plain text, bilingual via _ar / _en

    Media upload:
        Send multipart/form-data with home_hero[video] and/or
        home_hero[poster]. The files go to Cloudinary and the resulting full
        URLs land in video_url / poster_url. Browsers cannot send
        multipart with PUT, so use POST plus a _method=PUT field:

            const fd = new FormData();
            fd.append('_method', 'PUT');
            fd.append('home_hero[poster]', file);

        video   mp4 / webm / mov, up to 50MB
        poster  image, up to 4MB

    Returns:  200 + the full updated Settings object
              401 if not logged in
              403 if the account is not an admin
              422 + { message, errors } on validation failure

--------------------------------------------------------------------------------
Settings object shape:
{
  "brand": {
    "site_url": "https://durjewels.com",
    "whatsapp_number": "963999000000"
  },
  "contact": {
    "phone": "+963 999 000 000",
    "phone_href": "tel:+963999000000",
    "email": "info@dur-jewelry.com",
    "address_ar": "دمشق، سوريا",
    "address_en": "Damascus, Syria"
  },
  "social": {
    "instagram_url": "https://instagram.com/dur.jewelry",
    "facebook_url": "https://facebook.com/dur.jewelry"
  },
  "home_hero": {
    "video_url": "<full cloudinary url>" | null,
    "poster_url": "<full cloudinary url>" | null,
    "title_line1_ar": "...",       "title_line1_en": "...",
    "title_line2_ar": "...",       "title_line2_en": "...",
    "description_ar": "...",       "description_en": "...",
    "primary_button_label_ar": "...",   "primary_button_label_en": "...",
    "primary_button_url": "/products",
    "secondary_button_label_ar": "...", "secondary_button_label_en": "...",
    "secondary_button_url": "/#about"
  }
}

Note: "social" has NO WhatsApp entry on purpose. Build that link from
brand.whatsapp_number as `https://wa.me/{whatsapp_number}` - a second field
would only be a copy that can drift out of sync.

================================================================================
PRODUCTS
================================================================================

GET /api/products
    Auth:     none - public, no login required
    Query params (all optional):
        category_id   string   - category slug (preferred) or numeric id,
                                 e.g. category_id=rings or category_id=3.
                                 An unknown category returns an empty list.
        is_active     boolean
        search        string   - matches against name_ar OR name_en
        per_page      integer  - default 15
    Returns:  paginated list
              { data: Product[], links: {...}, meta: {...} }

--------------------------------------------------------------------------------

GET /api/products/{product}
    Auth:     none - public, no login required
    Path:     product = slug (preferred) or numeric id
              e.g. /api/products/gold-ring-21k  or  /api/products/12
    Returns:  a single Product

--------------------------------------------------------------------------------

POST /api/products
    Auth:     admin or manager
    Body:     multipart/form-data
        category_id       required  integer, must exist in categories
        slug              required  string, max 255, unique across products
        name_ar           required  string, max 255
        name_en           required  string, max 255
        description_ar    optional  string
        description_en    optional  string
        gold_weight       optional  numeric, >= 0
        karat             optional  one of: 18, 21, 22, 24
        gemstone_type     optional  string, max 255
        gemstone_carat    optional  numeric, >= 0
        price             required  numeric, >= 0
        has_discount      optional  boolean, defaults false. Switches the
                                    manual discount on.
        discount_value    required when has_discount is true
                                    numeric percentage, 0.01 - 100
        stock             optional  integer, >= 0
        is_active         optional  boolean
        images[]          optional  array of image files, max 4MB each
    Returns:  201 + the created Product (with images/category loaded)

--------------------------------------------------------------------------------

PUT /api/products/{product}
    Auth:     admin or manager
    Path:     product = slug (preferred) or numeric id
    Body:     multipart/form-data - same fields as POST above, but all optional
              (only send the fields you want to change)
    Note:     any images[] sent here are ADDED to the product's existing
              images - they do NOT replace them. Use the delete-image endpoint
              below to remove one first if needed.
    Note:     this is how a discount gets applied in the current flow. Send
              { "has_discount": true, "discount_value": 15 } to put 15% off
              this product, and { "has_discount": false } to stop it -
              discount_value is kept, so switching it back on later needs
              has_discount alone.
    Returns:  200 + the updated Product

--------------------------------------------------------------------------------

PATCH /api/products/{product}/toggle-active
    Auth:     admin or manager
    Path:     product = slug (preferred) or numeric id
    Body:     none
    Effect:   flips is_active (true <-> false)
    Returns:  200 + the updated Product

--------------------------------------------------------------------------------

DELETE /api/products/{product}
    Auth:     admin only
    Path:     product = slug (preferred) or numeric id
    Effect:   deletes the product AND all its images from Cloudinary
    Returns:  200 + { message }

--------------------------------------------------------------------------------

DELETE /api/products/{product}/images/{image}
    Auth:     admin or manager
    Path:     product = slug (preferred) or numeric id
              image   = product_image id (integer)
    Effect:   deletes one image. If it was the primary image (is_primary),
              the next remaining image (by sort_order) automatically becomes
              primary.
    Returns:  200 + { message }

--------------------------------------------------------------------------------
Product object shape:
{
  "id": 1,
  "slug": "gold-ring-21k",
  "category_id": 1,
  "category": { ...Category object, see below... },
  "name_ar": "...",
  "name_en": "...",
  "description_ar": "..." | null,
  "description_en": "..." | null,
  "gold_weight": 5.5 | null,
  "karat": "18" | "21" | "22" | "24" | null,
  "gemstone_type": "..." | null,
  "gemstone_carat": 0.5 | null,
  "price": 500.75,          // the original price, never discounted
  "has_discount": true,     // is the manual per-product discount switched on
  "discount_value": 20,     // the manual discount percentage (kept even when off)
  "final_price": 400.60,    // the price to display
  "discount": null | {      // null when nothing applies
    "source": "product" | "promotion",
    "type": "percentage" | "fixed",
    "value": 20,
    "amount": 100.15,       // currency taken off THIS product
    "promotion_id": 1 | null,      // null when source is "product"
    "name_ar": "تخفيضات العيد" | null,
    "name_en": "Eid Sale" | null,
    "ends_at": "2026-09-01T00:00:00+00:00" | null
  },
  "stock": 10,
  "is_active": true,
  "images": [ { "id": 1, "path": "<full cloudinary url>", "sort_order": 0, "is_primary": true }, ... ],
  "created_at": "2026-01-01T12:00:00+00:00",
  "updated_at": "2026-01-01T12:00:00+00:00"
}
Note: "images[].path" is the full, ready-to-use Cloudinary image URL - not a
relative path. Use it directly as an <img src>.

Note: always display "final_price". It equals "price" when nothing is on
offer, so it is safe to show unconditionally. Show "price" struck through
only when "discount" is not null. Promotions that need a code are NEVER
reflected here - see POST /api/promotions/validate.

There are two independent discount sources and they NEVER stack - whichever
gives the bigger reduction wins, and "discount.source" tells you which one
it was:

  "product"    the manual per-product discount (has_discount +
               discount_value). This is how the current version works: the
               customer sends a product link over WhatsApp and management
               sets a discount on that product.

  "promotion"  a running automatic campaign from the promotions section
               below. Built for later use.

"has_discount" and "discount_value" describe only the manual discount. Do
not compute prices from them - "final_price" already accounts for both
sources.

CATEGORIES
================================================================================

GET /api/categories
    Auth:     none - public, no login required
    Params:   none
    Returns:  array of ALL categories (no pagination)

--------------------------------------------------------------------------------

GET /api/categories/{category}
    Auth:     none - public, no login required
    Path:     category = slug (preferred) or numeric id
              e.g. /api/categories/rings  or  /api/categories/12
    Returns:  a single Category

--------------------------------------------------------------------------------

POST /api/categories
    Auth:     admin or manager
    Body:     multipart/form-data
        name_ar    required  string, max 255
        name_en    required  string, max 255
        slug       required  string, max 255, unique across categories
        image      optional  single image file, max 4MB
        is_active  optional  boolean
    Returns:  201 + the created Category

--------------------------------------------------------------------------------

PUT /api/categories/{category}
    Auth:     admin or manager
    Path:     category = slug (preferred) or numeric id
    Body:     multipart/form-data - same fields as POST above, but all optional
    Note:     uploading a new "image" REPLACES the old one (unlike products,
              a category only has one image).
    Returns:  200 + the updated Category

--------------------------------------------------------------------------------

DELETE /api/categories/{category}
    Auth:     admin only
    Path:     category = slug (preferred) or numeric id
    Effect:   also deletes every product that belongs to this category
              (cascade)
    Returns:  200 + { message }

--------------------------------------------------------------------------------
Category object shape:
{
  "id": 1,
  "image": "<full cloudinary url>" | null,
  "name_ar": "...",
  "name_en": "...",
  "slug": "rings",
  "is_active": true,
  "products_count": 12   // only present from GET /api/dashboard/stats, null elsewhere
}

================================================================================
PROMOTIONS & DISCOUNT CODES  (built for a later version)
================================================================================

Not part of the current WhatsApp flow - day-to-day discounts are set per
product via PUT /api/products/{product}. These endpoints work today and can
be left unused until they are needed.

A promotion is either AUTOMATIC or CODE-BASED - the difference is one field:

    code = null   automatic. Applies on its own; the discounted price shows
                  up as "final_price" on every product it covers.
    code = "..."  the customer must type the code. It NEVER changes the
                  prices returned by the product endpoints.

Each promotion covers one of three scopes:

    all          the whole store
    products     only the products listed in product_ids
    categories   every product in the listed categories - including products
                 added to those categories later

A promotion counts as running when is_active is true AND "now" sits inside
starts_at..ends_at. Either date may be null, meaning open-ended on that side.

When several automatic promotions cover the same product the customer gets
the largest discount; they never stack.

--------------------------------------------------------------------------------

GET /api/promotions/active
    Auth:     none - public, no login required
    Params:   none
    Returns:  array of running AUTOMATIC promotions - for banners and badges
    Note:     code-based promotions are deliberately excluded, otherwise the
              codes would be readable by anyone

--------------------------------------------------------------------------------

POST /api/promotions/validate
    Auth:     none - public, no login required
    Body:     { "code": "EID2026" }   required, max 50 chars, case-insensitive
    Returns:  200 + {
                "promotion": { ...Promotion... },
                "products": [ ...Product... ] | null   // null = whole store
              }
              404 + { message } if the code is unknown, disabled, or outside
                                its dates (one shared message on purpose, so
                                codes cannot be guessed by trial and error)
              422 + { message, errors } if no code was sent

--------------------------------------------------------------------------------

GET /api/promotions
    Auth:     admin or manager
    Query params (optional):
        running   boolean - true: only promotions live right now
                            false: only those that are not
    Returns:  array of ALL promotions (no pagination)

--------------------------------------------------------------------------------

GET /api/promotions/{promotion}
    Auth:     admin or manager
    Path:     promotion = numeric id
    Returns:  a single Promotion

--------------------------------------------------------------------------------

POST /api/promotions
    Auth:     admin or manager
    Body:     application/json
        name_ar        required  string, max 255
        name_en        required  string, max 255
        code           optional  string, max 50, letters/numbers/-/_ only,
                                 unique. Stored and matched uppercase.
                                 OMIT IT for an automatic promotion.
        type           required  "percentage" or "fixed"
        value          required  numeric, >= 0.01
                                 capped at 100 when type is "percentage"
        scope          required  "all", "products", or "categories"
        product_ids    required when scope = "products"     array of product ids
        category_ids   required when scope = "categories"   array of category ids
        starts_at      optional  ISO-8601 datetime. Omit to start immediately.
        ends_at        optional  ISO-8601 datetime, not before starts_at.
                                 Omit for no expiry.
        is_active      optional  boolean, defaults to true
    Returns:  201 + the created Promotion

--------------------------------------------------------------------------------

PUT /api/promotions/{promotion}
    Auth:     admin or manager
    Path:     promotion = numeric id
    Body:     same fields as POST, all optional - send only what changes
    Note:     product_ids / category_ids REPLACE the current selection, they
              do not add to it. Changing scope clears the links that no
              longer apply.
    Returns:  200 + the updated Promotion

--------------------------------------------------------------------------------

PATCH /api/promotions/{promotion}/toggle-active
    Auth:     admin or manager
    Path:     promotion = numeric id
    Body:     none
    Effect:   flips is_active without touching the dates - the quickest way
              to stop a live promotion
    Returns:  200 + the updated Promotion

--------------------------------------------------------------------------------

DELETE /api/promotions/{promotion}
    Auth:     admin only
    Path:     promotion = numeric id
    Effect:   deletes the promotion and its product/category links. Products
              and categories themselves are untouched.
    Returns:  200 + { message }

--------------------------------------------------------------------------------
Promotion object shape:
{
  "id": 1,
  "name_ar": "تخفيضات العيد",
  "name_en": "Eid Sale",
  "code": "EID2026" | null,      // null = applies automatically
  "type": "percentage" | "fixed",
  "value": 20,                   // percent, or a currency amount when fixed
  "scope": "all" | "products" | "categories",
  "starts_at": "2026-09-01T00:00:00+00:00" | null,
  "ends_at": "2026-09-10T00:00:00+00:00" | null,
  "is_active": true,
  "is_running": true,            // active AND inside its dates right now
  "products": [ ...Product... ],    // only when scope = "products"
  "categories": [ ...Category... ], // only when scope = "categories"
  "created_at": "2026-01-01T12:00:00+00:00",
  "updated_at": "2026-01-01T12:00:00+00:00"
}

WEBHOOKS (not used by the frontend)
================================================================================

POST /api/webhooks/clerk
    Auth:     none - instead protected by a Svix signature check
    Called by: Clerk only (configured in the Clerk dashboard), never by the
              frontend directly
    Required headers: svix-id, svix-timestamp, svix-signature
    Body:     raw Clerk event payload (JSON)
    Effect:   keeps the local users table in sync with Clerk. Three event
              types are handled; all three must stay subscribed in the
              Clerk dashboard:

                user.created  creates the local user (role: "customer").
                              If a row already uses that email, it is
                              linked to the new Clerk account instead,
                              keeping its existing role.

                user.updated  syncs name and email. An email already owned
                              by another row is skipped (name still syncs).
                              If the user is unknown, it is created.

                user.deleted  deletes the local row. Required: without it
                              the row outlives the Clerk account and blocks
                              anyone from signing up with that email again.

              Any other event type is accepted and ignored.
    Returns:  200 + { message }  on success, and for ignored event types
              400 + { message }  if the signature is invalid
